## 1. システムの目的

小〜中規模のチーム（1 組織・利用者 5〜100 名程度）が、**「誰が・何を・いつまでに」行うのかを 1 か所で共有し、抜け漏れと期限超過を防ぐ** ための社内向けタスク管理システム。

Plane のような多機能プロジェクト管理ではなく、次の 3 点に絞る。

1. タスクを素早く登録し、担当者と期限をはっきりさせる
2. 自分がやるべきこと（期限切れ・今日・今週）をすぐに把握できる
3. プロジェクトの進み具合を一覧・ボード・ガントチャート・ステータス別円グラフで確認できる（ガント・円グラフは Phase 9 で追加）

## 2. 対象ユーザー

| 利用者 | 説明 | 主な関心 |
|---|---|---|
| メンバー | タスクを実行する一般社員 | 自分の担当タスク、期限、コメントでのやり取り |
| プロジェクト管理者 | プロジェクトの進行を管理するリーダー | 全体の進捗、担当の割り振り、期限超過の把握、メンバー・ステータス・タグの管理 |
| 閲覧者 | 関係部署・上長など | 進捗の確認のみ |
| システム管理者 | 情報システム担当 | 利用者アカウントの発行・停止・パスワード再発行 |

## 3. 利用目的・主要業務・主要タスク

| 主要業務 | 主要タスク（利用者の操作） |
|---|---|
| タスクの登録と割り振り | タスク作成、担当者・期限・優先度の設定、サブタスク分割 |
| 日々の実行 | 自分のタスク確認、ステータス更新、コメントでの報告・質問、ファイル添付 |
| 進捗管理 | 一覧の絞り込み・並べ替え、ボードでの状況把握、マイルストーン単位の進捗確認、ガントチャートでの日程の把握と調整、ステータス別円グラフでの割合の把握（Phase 9） |
| プロジェクト運営 | プロジェクト作成、メンバー招待とロール設定、ステータス・タグの整備、アーカイブ |
| アカウント管理 | 利用者の登録・停止・ロック解除・パスワード再発行 |

## 4. 利用シーン

- 朝、ホーム（自分のタスク）で「期限切れ」「今日まで」を確認して作業を決める
- 会議中にタスクを素早く登録し、担当者と期限をその場で決める
- 作業が終わったらタスクのステータスを「完了」にし、必要ならコメントで報告する
- リーダーが週次で、プロジェクトのボードと期限切れタスクを確認する
- お知らせで「自分に割り当てられた」「自分のタスクにコメントが付いた」ことに気付く
- PC が主だが、外出先でスマートフォンからステータス更新・コメントもできる

## 5. 管理対象

利用者アカウント、プロジェクト、プロジェクトメンバー、ステータス（プロジェクト毎のワークフロー）、タグ、マイルストーン、タスク（サブタスク含む）、コメント、添付ファイル、タスクの変更履歴、お知らせ、セキュリティ監査記録。

## 6. システム境界

```text
              ┌──────────────── TaskManager ────────────────┐
利用者(ブラウザ) ─HTTPS→ Web(SPA, 静的配信 + /api 中継) ─→ API(.NET 10) ─→ MySQL 8.4
                                                             └→ 添付ファイル保存領域（Docker ボリューム）
              └──────────────────────────────────────────────┘
```

- 外部システム連携（メール送信、外部認証、Webhook、外部 API 公開）は **対象外**（MVP）。
- 認証は TaskManager 自身のアカウント（メールアドレス + パスワード）で行う。

## 7. 対象外（MVP では実装しない）

| 対象外の機能 | 理由 | 将来の扱い |
|---|---|---|
| 複数組織（マルチテナント / ワークスペース階層） | 単一組織での利用を想定。階層を減らし分かりやすさを優先 | [open-decisions.md](open-decisions.md) OD-01 |
| 利用者の自己登録・メール認証・メールでのパスワード再設定 | SMTP を必須にしないため。管理者がアカウントを発行・再発行する | OD-08 |
| メール通知・Webhook・外部 API キー | 外部連携は MVP 範囲外 | OD-09 |
| リアルタイム共同編集・Wiki | 実装コストが高く、目的（抜け漏れ防止）に直結しない | 対象外 |
| サイクル（スプリント）とモジュールの二重管理 | 「マイルストーン」1 つに統合 | — |
| 受付（承認待ちの外部起票）・公開ボード | 社内利用のみ | 対象外 |
| カレンダー表示・分析ダッシュボード（ステータス以外の集計軸、推移・バーンダウン等の時系列集計、折れ線グラフ） | 表・ボード・ガント・ステータス別円グラフで足りる | OD-12。**ガントチャートとステータス別円グラフは Phase 9 で対象に追加**（§9.11） |
| タスクの依存関係（先行・後続） | ガントで扱うには新しい関係の保存が必要 | OD-32 |
| 手動並べ替え（ドラッグでの順序保存） | 優先度・期限での自動並びで十分と判断 | OD-11 |
| 複数担当者 | 責任の所在を明確にするため担当者は 1 名 | OD-04 |
| AI 機能・画像検索・テーマ | 目的外 | 対象外 |
| 多言語対応 | 日本語のみ（識別子は英語） | 対象外 |

## 8. 主要ユーザーフロー

### UF-01 初回利用
システム管理者がアカウント発行 → 利用者が一時パスワードでログイン → パスワード変更を強制 → ホーム（自分のタスク、空状態の案内）

### UF-02 タスク登録
プロジェクトのタスク一覧 →「タスクを追加」（またはキー `N`）→ タイトル入力（必須はタイトルのみ）→ 担当者・期限・優先度を必要に応じて設定 → 登録 → 一覧に即時反映、トースト「タスク PRJ-12 を追加しました」

### UF-03 日々の確認と更新
ホーム（期限切れ / 今日 / 今週 / それ以降 / 期限なし）→ タスクを開く → ステータスを変更 / コメント → ホームに戻る

### UF-04 進捗確認
プロジェクト → ボード表示（ステータス列）または 表表示で「期限切れ」「担当者別」に絞り込み → マイルストーン詳細で進捗率を確認

（Phase 9 で追加）プロジェクト → 表示形式「ガント」で日程と期限切れを確認（担当者・ステータス・マイルストーンでまとめる）→ 遅れているタスクの棒をドラッグして日程を調整 → 表示形式「円グラフ」でステータスごとの割合を確認 → 凡例のステータス名から、そのステータスのタスクの表へ移動

（Phase 9 で追加）ホーム（自分のタスク）→「ステータス別の割合」で自分の担当の進み具合を確認

### UF-05 プロジェクト立ち上げ
プロジェクト一覧 →「プロジェクトを作成」→ 名前とキー（例 `SALES`）→ 既定ステータス自動作成 → メンバー追加（ロール選択）→ タグ・マイルストーン作成

### UF-06 アカウント停止
システム管理者 → 利用者管理 → 対象を「利用停止」→ 確認ダイアログ → 即時ログイン不可・既存セッション無効

## 9. 機能要件

凡例: 重要度 **Must**（MVP 必須）/ **Should**（MVP に含めるが優先度は下）/ **Could**（余力があれば）
権限の略号: SA=システム管理者、OW=プロジェクト管理者、ED=編集者、VW=閲覧者、本人=操作者自身
Entity / API / 画面の名前は [naming-rules.md](naming-rules.md)・[domain-model.md](domain-model.md)・[api-design.md](api-design.md)・[ui-design.md](ui-design.md) に対応する。

### 9.1 認証・アカウント

#### REQ-AUTH-01 ログイン（Must）
- 目的: 本人確認を行い、システムを利用可能にする
- 利用者: 全利用者
- 前提: アカウントが有効（停止されていない）
- 入力: メールアドレス、パスワード
- 処理: メールアドレスを正規化（前後空白除去・小文字化）して照合、パスワードハッシュ検証、失敗回数の記録とロック判定、アクセストークン発行、リフレッシュセッション作成、監査記録
- 出力: アクセストークン（15 分）、リフレッシュ Cookie、利用者情報（パスワード変更要否を含む）
- エラー: 入力不足（400）、認証失敗（401、「メールアドレスまたはパスワードが正しくありません」— 存在有無を区別しない）、ロック中（423 ではなく 401 + コード `auth.locked`）、試行過多（429）
- 権限: 未認証で利用可
- 関連 Entity: UserAccount, RefreshSession, SecurityAuditEvent
- 関連 API: `POST /api/v1/auth/login`
- 関連画面: SCR-01 ログイン

#### REQ-AUTH-02 ログイン状態の維持（Must）
- 目的: 再ログインの手間を減らしつつ安全性を保つ
- 前提: 有効なリフレッシュ Cookie
- 処理: リフレッシュトークンのローテーション（使用済みトークン再利用を検知したら同系列の全セッション失効）
- 出力: 新しいアクセストークン、新しいリフレッシュ Cookie
- エラー: 期限切れ・失効・再利用検知（401）
- 関連 API: `POST /api/v1/auth/refresh`
- 関連 Entity: RefreshSession

#### REQ-AUTH-03 ログアウト（Must）
- 処理: 現在のリフレッシュセッションを失効、Cookie 削除
- 出力: 204
- 関連 API: `POST /api/v1/auth/logout`、画面: ヘッダーの利用者メニュー

#### REQ-AUTH-04 パスワード変更（Must）
- 目的: 本人によるパスワード変更、および一時パスワードからの切替
- 入力: 現在のパスワード、新しいパスワード
- 処理: 現在パスワード検証、パスワードポリシー検証（[authentication-authorization.md](authentication-authorization.md) §5）、ハッシュ更新、変更要否フラグ解除、他の全セッション失効、監査記録
- 出力: 新しいアクセストークンとリフレッシュ Cookie（操作した端末はログインしたまま）
- エラー: 現在パスワード不一致（400 `auth.current_password_invalid`）、ポリシー違反（400）
- 権限: 本人
- 関連 API: `POST /api/v1/auth/password`、画面: SCR-02 パスワード変更、SCR-16 個人設定

#### REQ-AUTH-05 一時パスワード利用時の変更強制（Must）
- 処理: `mustChangePassword` が真の利用者は、パスワード変更・ログアウト・自分の情報取得以外の API を 403 `auth.password_change_required` で拒否。Frontend は SCR-02 へ誘導

#### REQ-AUTH-06 ログイン失敗時のロック（Must）
- 処理: 連続 5 回失敗で 15 分ロック。ロック中は正しいパスワードでもログイン不可。SA は解除可能
- 関連: REQ-USR-05

### 9.2 利用者管理（システム管理者）

#### REQ-USR-01 利用者一覧（Must）
- 入力: 検索語（表示名・メール）、状態（有効/停止/ロック中）、ページ
- 出力: 利用者の一覧（表示名、メール、システムロール、状態、最終ログイン日時）
- 権限: SA
- API: `GET /api/v1/users`、画面: SCR-17 利用者管理

#### REQ-USR-02 利用者の発行（Must）
- 入力: メールアドレス（必須・一意）、表示名（必須、1〜50 文字）、システムロール
- 処理: 一時パスワードを生成（16 文字、英大小数字記号）し、`mustChangePassword=true` で作成。一時パスワードは **応答で 1 回だけ** 返す（DB には平文を保存しない、ログに出さない）
- 出力: 201、利用者情報 + 一時パスワード
- エラー: メール重複（409 `user.email_taken`）、形式不正（400）
- 権限: SA
- API: `POST /api/v1/users`、画面: SCR-17（発行ダイアログ → 一時パスワード表示ダイアログ「この画面を閉じると再表示できません」）

#### REQ-USR-03 利用者情報の変更（Must）
- 入力: 表示名、システムロール
- エラー: 最後の SA を一般利用者に変更しようとした（409 `user.last_administrator`）
- 権限: SA
- API: `PATCH /api/v1/users/{userId}`

#### REQ-USR-04 利用停止・再開（Must）
- 処理: 停止時は全リフレッシュセッション失効。停止中は担当者に新規設定できない。既存の担当・履歴は保持
- エラー: 自分自身の停止（409 `user.cannot_deactivate_self`）、最後の SA の停止（409）
- API: `POST /api/v1/users/{userId}/deactivate`、`POST /api/v1/users/{userId}/activate`

#### REQ-USR-05 ロック解除（Must）
- API: `POST /api/v1/users/{userId}/unlock`、権限: SA

#### REQ-USR-06 パスワード再発行（Must）
- 処理: 新しい一時パスワードを生成、変更強制、全セッション失効、監査記録。応答で 1 回だけ返す
- API: `POST /api/v1/users/{userId}/password-reset`、権限: SA

#### REQ-USR-07 自分のプロフィール（Must）
- 入力: 表示名、タイムゾーン（既定 `Asia/Tokyo`）
- API: `GET /api/v1/me`、`PATCH /api/v1/me`、画面: SCR-16
- 権限: 本人

#### REQ-USR-08 利用者の検索（メンバー追加用）（Must）
- 目的: プロジェクトにメンバーを追加する際に利用者を探す
- 出力: 有効な利用者の ID・表示名・メール（最大 20 件）
- 権限: いずれかのプロジェクトの OW、または SA
- API: `GET /api/v1/user-directory?q=`

#### REQ-USR-09 初期システム管理者の作成（Must）
- 処理: 起動時、SA が 1 人も存在しない場合のみ、環境変数で指定されたメール・初期パスワードで SA を作成（`mustChangePassword=true`）。既に存在すれば何もしない
- 関連: [migration-strategy.md](migration-strategy.md) §6

### 9.3 プロジェクト

#### REQ-PRJ-01 プロジェクト一覧（Must）
- 出力: 自分が参加しているプロジェクト（名前、キー、自分のロール、未完了タスク数、期限切れ数）。アーカイブ済みは切替で表示
- 権限: 認証済み（SA はすべてのプロジェクトの名前・キー・管理者を参照可能。内容は参照不可）
- API: `GET /api/v1/projects`、画面: SCR-05

#### REQ-PRJ-02 プロジェクト作成（Must）
- 入力: 名前（1〜80 文字、組織内一意）、キー（2〜10 文字、英大文字で始まる英大文字・数字、組織内一意、**作成後変更不可**）、説明（任意、2,000 文字）
- 処理: 作成者を管理者（OW）として登録、既定ステータス 5 件を作成（[domain-model.md](domain-model.md) §4.3）
- エラー: キー重複（409 `project.key_taken`）、名前重複（409 `project.name_taken`）、形式不正（400）
- 権限: 認証済みの全利用者（OD-02）
- API: `POST /api/v1/projects`、画面: SCR-05（作成ダイアログ）

#### REQ-PRJ-03 プロジェクト情報の変更（Must）
- 入力: 名前、説明、`version`（楽観的排他）
- エラー: 競合（409 `concurrency.conflict`）
- 権限: OW
- API: `PATCH /api/v1/projects/{projectKey}`、画面: SCR-12

#### REQ-PRJ-04 アーカイブ / 復元（Must）
- 処理: アーカイブ中は全員読み取り専用（復元のみ可）
- 権限: OW
- API: `POST .../archive`、`POST .../unarchive`

#### REQ-PRJ-05 プロジェクト削除（Should）
- 前提: アーカイブ済み
- 処理: 全関連データと添付ファイルを物理削除。確認ダイアログでキーの入力を要求
- 権限: SA のみ
- API: `DELETE /api/v1/projects/{projectKey}`

### 9.4 プロジェクトメンバー

#### REQ-MEM-01 メンバー一覧（Must）
- 権限: VW 以上（担当者選択に使うため）
- API: `GET /api/v1/projects/{projectKey}/members`

#### REQ-MEM-02 メンバー追加（Must）
- 入力: 利用者 ID、ロール（管理者 / 編集者 / 閲覧者）
- エラー: 既にメンバー（409 `member.already_exists`）、停止中の利用者（400 `member.user_inactive`）
- 処理: 追加された利用者にお知らせ
- 権限: OW、SA（管理者不在時の救済用）
- API: `POST .../members`、画面: SCR-13

#### REQ-MEM-03 ロール変更（Must）
- エラー: 最後の管理者を降格（409 `member.last_owner`）
- 権限: OW、SA
- API: `PATCH .../members/{userId}`

#### REQ-MEM-04 メンバー削除・自分の脱退（Must）
- 処理: 削除された利用者が担当のタスクは **担当者なし** に戻し、履歴を残す
- エラー: 最後の管理者（409 `member.last_owner`）
- 権限: OW、SA、本人（脱退）
- API: `DELETE .../members/{userId}`

### 9.5 ステータス・タグ

#### REQ-STS-01 ステータスの一覧・作成・変更・並べ替え（Must）
- 入力: 名前（1〜30 文字、プロジェクト内一意）、区分（未着手 / 進行中 / 完了 / 中止）、色（定義済みパレットから選択）、既定かどうか
- 制約: 1 プロジェクト最大 20 件。既定ステータスは常に 1 件で、区分は「未着手」または「進行中」
- 権限: 一覧は VW 以上、変更は OW
- API: `GET/POST .../statuses`、`PATCH .../statuses/{statusId}`、`PUT .../statuses/order`、画面: SCR-14

#### REQ-STS-02 ステータスの削除（Must）
- 入力: 移動先ステータス（そのステータスのタスクが存在する場合は必須）
- エラー: 既定ステータスの削除（409 `status.is_default`）、移動先未指定（409 `status.in_use`）、最後の 1 件（409）
- 処理: タスクを移動先へ変更し履歴を残す

#### REQ-TAG-01 タグの管理（Should）
- 入力: 名前（1〜30 文字、プロジェクト内一意）、色
- 制約: 1 プロジェクト最大 50 件、1 タスク最大 10 件
- 権限: 一覧は VW 以上、作成・変更・削除は OW / ED
- API: `GET/POST .../tags`、`PATCH/DELETE .../tags/{tagId}`、画面: SCR-14

### 9.6 マイルストーン

#### REQ-MLS-01 マイルストーンの管理（Should）
- 入力: 名前（1〜80 文字、プロジェクト内一意）、説明（2,000 文字）、目標日（任意）、状態（進行中 / 終了）
- 出力: 進捗（完了 + 中止 タスク数 / 全タスク数）、期限切れタスク数
- 処理: 削除時はタスクとの関連を外す（タスク自体は残す）
- 権限: 参照 VW 以上、作成・変更・削除 OW / ED
- API: `GET/POST .../milestones`、`GET/PATCH/DELETE .../milestones/{milestoneId}`、画面: SCR-10, SCR-11

### 9.7 タスク

#### REQ-TSK-01 タスク作成（Must）
- 入力: タイトル（必須、1〜200 文字）、説明（Markdown、20,000 文字）、ステータス（省略時は既定）、優先度（省略時「中」）、担当者（任意、プロジェクトの OW / ED であること）、開始日・期限（任意、開始日 ≤ 期限）、タグ（任意、最大 10）、マイルストーン（任意）、親タスク（任意、同一プロジェクト・親自身がサブタスクでないこと）
- 処理: プロジェクト内連番を採番し `キー-番号`（例 `SALES-12`）を付与、履歴「作成」記録、担当者が自分以外ならお知らせ
- 出力: 201、タスク詳細
- エラー: 検証エラー（400、項目別メッセージ）、アーカイブ中（409 `project.archived`）
- 権限: OW / ED
- API: `POST /api/v1/projects/{projectKey}/tasks`、画面: SCR-09 タスク作成ダイアログ

#### REQ-TSK-02 タスク一覧（Must）
- 入力: フィルタ（ステータス、区分、担当者、担当者なし、自分の担当、優先度、タグ、マイルストーン、期限範囲、期限切れ、親/サブ、キーワード）、並べ替え、ページ（既定 50 件、最大 100 件）
- 出力: タスク概要の一覧と総件数
- 権限: VW 以上
- API: `GET /api/v1/projects/{projectKey}/tasks`、画面: SCR-06（表）、SCR-07（ボード）

#### REQ-TSK-03 タスク詳細（Must）
- 出力: 全項目、サブタスク一覧、作成者・更新者、`version`
- エラー: 存在しない、または参照権限なし（どちらも 404。存在の有無を漏らさない）
- API: `GET .../tasks/{taskNumber}`、画面: SCR-08

#### REQ-TSK-04 タスク更新（Must）
- 入力: 変更したい項目のみ + `version`
- 処理: 項目ごとに履歴、担当者変更時は新担当者へお知らせ、完了区分のステータスへ変更時は `completedAt` 設定（完了以外へ戻すと消去）、作成者（自分以外）へ完了お知らせ
- エラー: 競合（409 `concurrency.conflict`、Frontend は「他の人が先に更新しました。最新の内容を読み込みますか？」）、検証エラー（400）
- 権限: OW / ED
- API: `PATCH .../tasks/{taskNumber}`

#### REQ-TSK-05 タスク削除（Must）
- 処理: 物理削除（コメント・履歴・添付・タグ付けも削除）。サブタスクがある場合は `includeSubtasks=true` 指定時のみ一緒に削除
- エラー: サブタスクあり・未指定（409 `task.has_subtasks`）
- 権限: OW、または自分が作成したタスクの ED
- API: `DELETE .../tasks/{taskNumber}`、画面: SCR-08（削除確認ダイアログ）

#### REQ-TSK-06 サブタスク（Must）
- 制約: 階層は 1 段のみ（サブタスクの下にサブタスクは作れない）、親と同じプロジェクト
- 出力: 親の詳細でサブタスクの一覧と完了数を表示

#### REQ-TSK-07 タスクの変更履歴（Must）
- 出力: 日時の新しい順、ページ（50 件）。「山田さんがステータスを『進行中』から『完了』に変更しました」の形で表示
- 権限: VW 以上
- API: `GET .../tasks/{taskNumber}/history`

#### REQ-TSK-08 ボードでのステータス変更（Must）
- 処理: ドラッグ&ドロップ、またはキーボード操作（カードのメニュー「ステータスを変更」）で REQ-TSK-04 を呼ぶ
- 画面: SCR-07

#### REQ-TSK-09 キーでのタスク表示（Should）
- 目的: 「SALES-12」と伝えれば誰でも開ける
- 画面 URL: `/projects/SALES/tasks/12`、検索欄に `SALES-12` と入力で直接移動

### 9.8 コメント・添付

#### REQ-CMT-01 コメント（Must）
- 入力: 本文（Markdown、1〜10,000 文字）
- 処理: 担当者・作成者（投稿者本人を除く）へお知らせ
- 権限: 参照 VW 以上、投稿 OW / ED、編集は投稿者本人のみ、削除は投稿者本人または OW
- 表示: 編集済みなら「（編集済み）」
- API: `GET/POST .../tasks/{taskNumber}/comments`、`PATCH/DELETE .../comments/{commentId}`

#### REQ-ATT-01 添付ファイル（Should）
- 入力: ファイル（1 件 10MB まで、許可された種類のみ、1 タスク 20 件まで）
- 処理: 保存名は推測不能な ID、元のファイル名は表示用に保存、内容の種類（先頭バイト）を検証
- 出力: 一覧（名前、サイズ、登録者、日時）、ダウンロード（常にダウンロード扱い）
- エラー: サイズ超過（413 `attachment.too_large`）、種類不可（415 `attachment.type_not_allowed`）、件数超過（409）
- 権限: 参照・ダウンロード VW 以上、追加 OW / ED、削除は登録者本人または OW
- API: `GET/POST .../tasks/{taskNumber}/attachments`、`GET .../attachments/{attachmentId}/content`、`DELETE .../attachments/{attachmentId}`

### 9.9 自分のタスク・お知らせ・検索

#### REQ-MY-01 自分のタスク（ホーム）（Must）
- 出力: 参加中（アーカイブ除く）の全プロジェクトで自分が担当の未完了タスクを「期限切れ / 今日 / 今週（明日〜日曜）/ それ以降 / 期限なし」に分類。期限判定は利用者のタイムゾーンで行う。「完了したタスクも表示」で直近 7 日の完了分を表示
- API: `GET /api/v1/me/tasks`、画面: SCR-04

#### REQ-NTC-01 お知らせ（Must）
- 発生条件: (1) 自分が担当者に設定された、(2) 自分が担当者または作成者のタスクにコメントが付いた、(3) 自分が作成したタスクが完了した、(4) プロジェクトに追加された。いずれも **操作者本人には通知しない**
- 出力: 一覧（未読のみ切替）、未読件数（ヘッダーのベル、60 秒ごと + 画面復帰時に更新）
- 処理: 個別既読、すべて既読。90 日経過したお知らせは自動削除
- API: `GET /api/v1/me/notices`、`GET /api/v1/me/notices/unread-count`、`POST /api/v1/me/notices/{noticeId}/read`、`POST /api/v1/me/notices/read-all`
- 画面: SCR-15、ヘッダーのお知らせパネル

#### REQ-SRC-01 タスク検索（Should）
- 入力: キーワード（1〜100 文字）。`SALES-12` 形式ならそのタスクを最優先
- 出力: 参加中プロジェクトのタスク（タイトル部分一致）最大 20 件
- API: `GET /api/v1/search/tasks?q=`、画面: ヘッダーの検索欄

### 9.10 監査

#### REQ-AUD-01 セキュリティ監査記録（Must）
- 記録対象: ログイン成功・失敗・ロック、ログアウト、パスワード変更・再発行、利用者の発行・停止・再開・ロール変更・ロック解除、リフレッシュトークン再利用検知、プロジェクトのメンバー・ロール変更、プロジェクト削除
- 出力: MVP では DB 保存とログ出力のみ（閲覧画面は OD-13）
- 保持: 1 年

### 9.11 ガントチャート・ステータス別円グラフ（Phase 9 で追加）

Phase 9 の指示（`.claude/skills/phase-09-correction/`）により追加した要件。対象外: 折れ線グラフ、推移・バーンダウン等の時系列集計、ステータス以外の集計軸（優先度・担当者など）の円グラフ、タスクの依存関係（OD-32）。
日付の扱いは既存方針（NFR-10）に従う: 開始日・期限は日付のみ（タイムゾーンなし）、「今日」と期限切れは利用者のタイムゾーン（既定 `Asia/Tokyo`）で判定する。新しい日時の保存項目はない。

#### REQ-GNT-01 ガントチャートの表示（Must）
- 名称: ガントチャート（プロジェクトのタスクの日程表示）
- 目的: タスクの開始日〜期限を時間軸の横棒で並べ、日程の重なり・遅れ・空きを一目で把握できるようにする
- 利用者: メンバー、プロジェクト管理者、閲覧者
- 前提: プロジェクトのメンバーである。タスクの開始日・期限（既存の項目）が設定されている
- 入力: 表示単位（日 / 週 / 月）、表示期間の基準日（前へ・次へ・今日で移動）、グループ（なし / 担当者 / ステータス / マイルストーン）、完了・中止も表示するか
- 処理:
  1. 表示単位から期間を決める（日: 14 日、週: 月曜始まりの 12 週、月: 12 か月）。期間は最大 366 日（OD-40）
  2. 期間と重なるタスクを取得する。棒の範囲は「開始日〜期限」。開始日だけ・期限だけのタスクはその 1 日の棒とし、欠けている日付を文字で示す
  3. 既定は未完了（未着手・進行中の区分）のみ。「完了・中止も表示」で全区分
  4. 期限切れ（終了区分以外で期限 < 今日）の棒は、警告色の枠 + ⚠ + 「◯日超過」の文字で区別する（色だけに頼らない）
  5. 今日の位置に縦線と「今日」の文字を表示する
  6. 開始日・期限がどちらもないタスクは「日付が未設定のタスク」の枠に別表示する（件数 + 先頭 50 件）
  7. グループ分け: 担当者（表示名順、担当者なしは最後）/ ステータス（ステータスの並び順）/ マイルストーン（目標日の近い順、なしは最後。目標日に ◆ の目印）
  8. 棒・行のタイトルからタスク詳細へ移動できる
- 出力: 時間軸（目盛り・今日の線）、行（タスクキー・タイトル・担当者）、棒（ステータスの色 + ステータス名の文字）、日付未設定の枠、表示件数の上限に達した場合の案内
- エラー: 存在しないプロジェクト・非メンバー（404 の画面）、期間の指定が不正（400。画面からは発生しない）、取得失敗（再試行できるエラー表示）
- 権限: 閲覧者以上（ViewProject）。アーカイブ中も閲覧できる
- 関連 Entity: TaskItem（StartDate, DueDate, StatusId, AssigneeUserId, MilestoneId）、WorkflowStatus、Milestone、UserAccount
- 関連 API: `GET /api/v1/projects/{projectKey}/tasks/schedule`（#62）、`GET .../statuses`、`GET .../milestones`
- 関連画面: SCR-20 タスク一覧（ガント）（`/projects/:projectKey/tasks?view=gantt`）
- 重要度: Must

#### REQ-GNT-02 ガントチャートでの日程変更（Should）
- 名称: 棒のドラッグによる日程変更
- 目的: 遅れたタスクの日程をその場で調整する
- 利用者: メンバー（編集者）、プロジェクト管理者
- 前提: 編集者以上、プロジェクトがアーカイブ中でない、タスクに開始日か期限がある
- 入力: 棒の移動（開始日と期限を同じ日数ずらす）、棒の右端の伸縮（期限のみ変更）。キーボード・支援技術では表形式の代替表示の日付欄で変更する
- 処理: 既存のタスク更新（REQ-TSK-04）を `startDate`・`dueDate`・`version` で呼ぶ。開始日 ≤ 期限（TK-02）はサーバーで検証し、画面でも期限が開始日より前にならないよう制限する。変更履歴（開始日・期限の変更）が残る
- 出力: 保存後の棒、失敗時のトースト
- エラー: 競合（409 `concurrency.conflict` →「他の人が先に更新しました。最新の内容を表示しています。」+ 再取得）、検証エラー（400）、アーカイブ中（409）、権限不足（403。通常は操作部品を出さない）
- 権限: 編集者以上（EditTasks）
- 関連 Entity: TaskItem、TaskHistoryEntry
- 関連 API: `PATCH /api/v1/projects/{projectKey}/tasks/{taskNumber}`（#44、既存）
- 関連画面: SCR-20
- 重要度: Should（OD-35）

#### REQ-GNT-03 ガントチャートの表形式の代替表示（Must）
- 名称: 日程の表
- 目的: 図を見られない・マウスを使えない利用者が同じ情報を得て、日程を変更できるようにする
- 利用者: 全利用者（特にキーボード・スクリーンリーダーの利用者）
- 前提: REQ-GNT-01 と同じ
- 入力: 「表で見る」の切り替え。編集者以上は開始日・期限の入力欄
- 処理: ガントと同じ行（同じグループ・同じ並び）を表で表示する
- 出力: キー、タイトル、ステータス、担当者、開始日、期限、日数、期限の状態（◯日超過 等）
- エラー・権限: REQ-GNT-01・02 と同じ
- 関連 API: #62、#44
- 関連画面: SCR-20
- 重要度: Must

#### REQ-CHT-01 プロジェクトのステータス別円グラフ（Must）
- 名称: ステータス別の割合（プロジェクト）
- 目的: プロジェクトのタスクがどのステータスに何件・何割あるかを把握する
- 利用者: メンバー、プロジェクト管理者、閲覧者
- 前提: プロジェクトのメンバーである
- 入力: なし（プロジェクトの全タスクが対象。サブタスクを含む）
- 処理:
  1. プロジェクトのステータス定義（名前・色・並び順・区分）をそのまま使う。新しいステータスは作らない
  2. ステータスごとの件数を DB で集計する（`GROUP BY status_id`）。0 件のステータスも含める
  3. 割合は件数 ÷ 合計を小数第 1 位で表し、最大剰余法で合計を 100.0% にそろえる（OD-36）
  4. タスクが 0 件なら空状態「まだタスクがありません」を表示する（円は描かない）
  5. 凡例（表）のステータス名から、そのステータスで絞り込んだ表へ移動できる（完了・中止の区分は「完了・中止も表示」を付ける。OD-41）
- 出力: 円グラフ（ステータスの色 + 白い区切り線）、凡例を兼ねる表（ステータス名・件数・割合）、合計件数、スクリーンリーダー向けの要約（「合計 12 件。未着手 5 件（41.7%）、…」）
- エラー: 非メンバー 404、取得失敗（再試行）
- 権限: 閲覧者以上（ViewProject）。アーカイブ中も閲覧できる（OD-37）
- 関連 Entity: TaskItem、WorkflowStatus
- 関連 API: `GET /api/v1/projects/{projectKey}/tasks/status-summary`（#63）
- 関連画面: SCR-21 タスク一覧（円グラフ）（`/projects/:projectKey/tasks?view=chart`）
- 重要度: Must

#### REQ-CHT-02 自分のタスクのステータス別円グラフ（Must）
- 名称: ステータス別の割合（自分のタスク）
- 目的: 自分が担当するタスクの進み具合（どのステータスに何割あるか）を把握する
- 利用者: 全利用者（本人）
- 前提: ログイン済み
- 入力: 対象（「すべてのプロジェクト」または参加中のプロジェクト 1 つ）
- 処理:
  1. 対象は、参加中かつアーカイブされていないプロジェクトで、自分が担当者のタスク（完了・中止を含む全区分）。他人の担当・非参加のプロジェクトは含めない
  2. 「すべてのプロジェクト」は、ステータスがプロジェクトごとに異なるため、ステータスの区分（未着手・進行中・完了・中止）で集計する。区分は既存のステータス定義（`StatusCategory`）の一部で、新しい分類は作らない（OD-34）
  3. プロジェクトを選んだ場合は、そのプロジェクトのステータス定義で集計する（0 件のステータスも含める）
  4. 件数は DB で集計し、割合・空状態・表示は REQ-CHT-01 と同じ規則
  5. プロジェクトを選んだ場合、凡例のステータス名から「担当者: 自分」で絞り込んだそのプロジェクトの表へ移動できる
- 出力: REQ-CHT-01 と同じ（円グラフ・表・合計・要約）
- エラー: 選んだプロジェクトに参加していない・存在しない（404 → 「対象が見つかりません」）、取得失敗（再試行）
- 権限: 本人（ログイン済み）。プロジェクト指定時は閲覧者以上
- 関連 Entity: TaskItem、WorkflowStatus、ProjectMembership、Project
- 関連 API: `GET /api/v1/me/tasks/status-summary`（#64、`projectKey` 任意）
- 関連画面: SCR-04 ホーム（自分のタスク）の表示「ステータス別の割合」（`/?view=chart`）
- 重要度: Must
